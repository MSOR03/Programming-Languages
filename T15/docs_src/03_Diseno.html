1. Arquitectura del emulador

El emulador se organiza en capas, siguiendo el modelo de una pila de protocolos. Las tres CPU solo se parecen en su frontera con la red: todas tienen una tarjeta de red (NIC) que transmite bytes; por encima de esa frontera, cada máquina es completamente distinta.

2. Diseño de los tres computadores

2.0 Comparación de los componentes von Neumann de cada fabricante

Los tres nodos respetan la arquitectura de John von Neumann (CPU con unidad de control y ALU, memoria única para programa y datos, unidad de entrada/salida y buses), pero ninguno de sus componentes coincide con el de los otros dos:

2.1 ANDES-64 (Industrias Andinas de Cómputo)

Es el computador de la Tarea 9, implementado en las Tareas 10/17 (codigo/andes64/): máquina de registros de 64 bits, 16 registros (R13 = SP, R14 = LR), banderas Z N C V I, RAM de 4 KB direccionable por byte en orden big-endian, cachés L1 (128 B) y L2 (512 B), bus de direcciones de 12 bits y 71 instrucciones en 6 formatos de 16 a 40 bits. Su NIC se maneja con:

NSEND Rn, buf     ; transmite Rn bytes desde buf       (formato F5, 36 bits)
NRECV Rn, buf     ; copia un paquete en buf; Rn ← su longitud (0 si no hay)

2.4 Formatos de instrucción comparados

El mismo cálculo (1 + 2 + … + n) se escribe de forma muy distinta en cada lenguaje ensamblador:

suma: CMP  R4, R2              pushb 0 swap          ( s n )        bucle: LDA n
      JG   fin_suma            bucle: dup jz fin_suma                      SUB i
      ADD  R3, R3, R4                 dup rot add swap ( s+n n )           JC  fin
      INC  R4                         pushb 1 sub      ( s+n n-1 )         LDA lo
      JMP  suma                       jmp bucle                            ADD i
                                                                           STA lo
                                                                           LDA hi
                                                                           ADC #0     ; acarreo
                                                                           STA hi
                                                                           LDA i
                                                                           ADD #1
                                                                           STA i
                                                                           JMP bucle

3. Interfaz común: NIC y PDU canónica

TipoNombreSemántica
1SUMA(n)Solicita al destino calcular 1 + 2 + … + n.
2RESULTADO(v)Respuesta a SUMA.
3PING(k)Solicitud de eco con número de secuencia k.
4PONG(k)Respuesta de eco.

Al transmitir, el byte 0 es el destino; la NIC lo retira y la red entrega al receptor el mismo mensaje con el byte 0 reemplazado por el origen. Así, un servidor responde simplemente cambiando el tipo y reenviando el búfer. Los enteros van en 32 bits big-endian (“orden de red”). Traducción en cada máquina:

  • ANDES-64 (big-endian, 64 bits): arma el entero byte a byte con desplazamientos (LEER_VALOR, ESCRIBIR_VALOR) y extiende el signo de 32 a 64 bits.
  • ORINOCO-32 (little-endian): load de 4 bytes seguido de bswap; al escribir, bswap y store.
  • CARIBE-16 (16 bits, por palabra): cada byte ocupa una palabra; el valor de 32 bits se reconstruye como dos palabras (hi:lo) con SHL #8 y OR.

4. Diseño de la red

4.1 Medio de radio y capa de enlace

  • Enlace entre i y j si distancia(i, j) ≤ min(alcancei, alcancej) (100 m).
  • Cada transmisión de un salto llega en el tick siguiente; se pierde con probabilidad p (independiente).
  • Unicast: hasta 3 intentos (ACK implícito); si fallan todos o el vecino está fuera de alcance, se notifica ruptura. Broadcast: un solo intento, cada vecino lo recibe o no independientemente.
  • Energía: 1 unidad por transmisión (incluidas retransmisiones), 0,5 por recepción.

4.2 Enrutamiento (AODV simplificado)

ParámetroValorSignificado
TTL12Saltos máximos de un RREQ.
VIDA_RUTA300 ticksTiempo de vida de una ruta sin uso (3 s).
ESPERA_RREP40 ticksEspera antes de reintentar el descubrimiento.
MAX_RREQ3Intentos de descubrimiento antes de descartar los paquetes pendientes.

Tabla de rutas por nodo: destino → [siguiente salto, saltos, expira]. Se aprende la ruta inversa con cada RREQ, la directa con cada RREP y también la ruta de vuelta con cada paquete de datos recibido. Simplificaciones respecto del RFC 3561: no se usan números de secuencia de destino (las rutas se reemplazan por una de menos saltos o del mismo vecino) y, en vez de RERR, el nodo que detecta la ruptura hace reparación local: borra las rutas que usaban ese vecino, guarda el paquete y busca una nueva ruta.

_recibir(nodo, emisor, p):
  si p es RREQ:   si (p.origen, p.id) ya visto: descartar
                  instalar ruta inversa origen → emisor (saltos + 1)
                  si nodo = p.destino: enviar RREP por la ruta inversa
                  si no y saltos < TTL: retransmitir por broadcast
  si p es RREP:   instalar ruta al origen del RREP → emisor
                  si nodo = destino del RREP: enviar los paquetes pendientes
                  si no: reenviar el RREP por la ruta inversa
  si p es DATOS:  instalar ruta de vuelta al origen
                  si nodo = p.destino: NIC.rx ← [origen] + datos ; registrar latencia
                  si no: _enviar_datos(nodo, p)          ; el nodo actúa como enrutador

4.3 Movilidad

Random waypoint en un área rectangular: destino uniforme, velocidad v (m/s) constante, pausa de 100 ticks (1 s) al llegar. Con v = 0 los nodos quedan fijos en posiciones aleatorias.
